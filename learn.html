How the profile page works:

Saving a profile needs three things: a table for the details, a bucket for the picture, and policies for who is allowed to do what. Get any one of them wrong and the page breaks in a different way each time.

1

The table: user_profiles

One row per person. It stores the username and the name of the image file, not the image itself.

column what it holds
id a number that counts up automatically
uuid who owns the row — filled in by the database
email from the sign-in session
username what the person typed
imagename the file path, e.g. 38cd…/1792….jpg 
create table public.user_profiles (
  id bigint generated always as identity primary key,
  uuid uuid not null default auth.uid(),
  email text not null unique,
  username text not null unique,
  imagename text not null
);
Why auth.uid() matters: The database reads it from the login token and fills it in. So nobody can create a row pretending to be someone else.
2

The bucket: avatars

A bucket is just a folder in Supabase Storage. Ours is called avatars, and every file sits inside a folder named after its owner: 

avatars/
  └── 38cd739a-821b-4b6d-adb5-d29abe0abf73/
        └── 1792558050912.jpg

Bucket settings:

  • Public: on, so the image can be shown with a plain URL
  • Size limit: about 500 KB per file
  • Types: any image: image/*
Making the bucket public lets anyone view a picture. It does not let anyone upload — that still needs a policy.
3

Policies:

Every table and bucket has Row Level Security. When it is on, the default answer to every request is no. Policies are the list of exceptions.

On user_profiles there are four, one per action. Each one asks the same question: does this row belong to the person asking?

create policy "Users can view own profile"
  on public.user_profiles for select
  using (auth.uid() = uuid);
  • Read: anyone, because the pictures are public
  • Upload / replace / delete: signed-in users only

Now the question everyone trips over: who is asking?

person database role auth.uid()
not signed in anon null
signed in authenticated their UUID

anon is the same as "not logged in". A policy comparing auth.uid() = uuid quietly refuses it.

Check the Role box when you make a policy. Left blank, it defaults to public, meaning everyone including anon.
4

The page, in order

Each step needs the one before it:

  • sign in, and read the session
  • pick a file, and check it in the browser
  • upload the file to avatars/<uuid>/
  • write the row with that path
const { data: { session } } = await db.auth.getSession();
const user = session.user;

const path = `${user.id}/${Date.now()}.jpg`;
await db.storage.from('avatars').upload(path, file);

await db.from('user_profiles').insert({
  email: user.email,
  username: username,
  imagename: path
});
The 400px×400px check is in JavaScript: the database can store a file but cannot measure one. The browser can detect the image dimensions before uploading.

Possible issues:

you see the problem is
"Bucket not found" the bucket exists but is not marked public
"new row violates row-level security policy" a policy is missing, or the Role is wrong
image saves, then shows broken after refresh the upload worked; the bucket is private

One last trap: getPublicUrl() does not check that a file exists. It just builds a URL. A broken image usually means the bucket flag, not the upload.
